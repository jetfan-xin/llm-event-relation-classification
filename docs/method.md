# Method and implementation

## Task definition

The input is an ordered event pair `(A, B)`. The output is one relation and a short explanation:

| Relation | Intended direction |
| --- | --- |
| `Causes` | A typically causes B |
| `HasSubevent` | B occurs as a component of A |
| `HasFirstSubevent` | A begins with B |
| `HasLastSubevent` | A ends with B |

These definitions follow the [ConceptNet relation documentation](https://github.com/commonsense/conceptnet5/wiki/Relations). The labels are treated as a four-way closed set for evaluation, although the underlying semantic relations can overlap.

## Archived experiment

The original collector requested up to ten 1,000-edge pages for each relation and retained edges whose start node was English. Its saved input contains 10,841 records before exclusions and 10,836 afterwards: four illustrative event pairs and one `dry -> dry` self-loop are removed. Up to 1,000 records per relation were processed in file order; no random evaluation split or training procedure is recorded.

The prompt combines definitions, one illustrative example per label, the two event labels and a JSON response template. The generator requests three independent responses. It selects the most frequent relation; when three different labels are returned, it makes a further request restricted to the tied candidates. Explanations accompany the predictions but are not independently validated evidence of model reasoning.

The script uses the model name `gpt-4o` through a third-party compatible endpoint. Model version, sampling settings, exact call costs and provider-side routing are not captured in the result files. The 3,999 stored records retain 11,997 initial responses; tie-break responses are represented by selected results rather than a separate raw-response log. That is not a complete API usage ledger.

## Maintained entry points

The `event_relations` package preserves the pipeline structure while making input validation, evaluation strategies and operational behavior explicit:

- `evaluation.py` normalizes `/r/Label`, `r/Label` and bare labels consistently. Unknown or missing predictions enter an `Invalid` confusion-matrix column instead of disappearing.
- `generation.py` uses exact canonical labels, requires a real majority, bounds tie-breaking to one additional call and abstains when valid selection fails. It parses complete JSON or fenced JSON without a brace-truncating regular expression.
- `runner.py` stores input and prompt hashes, model, endpoint and sampling configuration. It validates a checkpoint before resuming and writes completed pairs atomically. It does not swallow API failures as ordinary predictions.
- `collector.py` follows bounded pagination, validates the response host, checks both endpoint languages and retains attribution metadata in fresh collections.
- `graph.py` preserves concept IDs and parallel relation edges. It uses a documented undirected simple projection for k-core membership, then restores directed labelled edges for neighborhood inspection.

These are maintenance changes, not claims that the archived outputs were generated by the current entry points. The original results are kept unchanged.

## Prompt correction

The archived `Causes` example lists `A=fire` and `B=lighting a match`, while its explanation describes the reverse direction. The maintained `corrected` prompt swaps those example inputs. `--prompt-version historical` preserves the original wording. Neither option claims to recreate the old provider's exact model behavior.

An unused binary-existence prompt in the archive has contradictory examples and an inconsistent output schema. It is not part of the maintained experiment.

## Graph conventions and fixes

The archived visualizer traverses an undirected neighborhood but constructs a directed graph for k-core computation. NetworkX defines degree for a directed k-core using in-degree plus out-degree; see [the official k-core documentation](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.core.k_core.html). Its intermediate simple directed graph can collapse parallel relations, and its breadth-first traversal can omit edges between already visited nodes.

The maintained graph explicitly uses unique-neighbor degree in an undirected projection. It prunes nodes below `k`, chooses a deterministic highest-degree seed unless specified, expands a fixed number of hops and includes every directed labelled edge between the selected nodes. It excludes self-loops and reports their count. This definition differs from the archived directed-degree core and percentile/diameter filtering; results from those two graph procedures are not interchangeable.

Reference labels and selected model labels are separate options. Node identity uses ConceptNet IDs, not display labels; identical text therefore does not silently merge distinct concepts. The default archived-data example produces a 26-node, 30-edge neighborhood around `/c/en/eat`, from a core with 386 nodes. The same edge endpoints under both label views mean the topology remains the same, while relation labels can change.
